# OleGURPS QOL — оптимизация хранения истории выстрелов

23.10.2026. Foundry 14.364, GGA 0.18.23, модуль0.2.1. Версия и игровые формулы не менялись. Commit/push/merge/rebase/reset/tag/release не выполнялись.

## Выполнено

Устранены повторное глубокое копирование всего журнала расхода в рабочих операциях AmmoService, передача всего shotReceipts при изменении ресурсов и лишние полные профили в новых сообщениях. Все старые квитанции сохранены, без TTL, последних N записей, удаления оружия из истории или миграции ChatMessage. Добавлены долговечный pending-intent до броска, индекс незавершённых сообщений и кеш чистого описания сохранённого профиля с инвалидированием.

Итог: **836 уникальных PASS** в адресных тестах, без незакрытых FAIL. Настоящие Attack/Damage/HT проверены отдельно в Foundry GM и PLAYER/OWNER. Основное окно пользователя не разворачивалось, не активировалось и не перезагружалось: использовались фоновый debugger и изолированные headless-клиенты. Большие наборы100/1000/10000 создавались только в Node fixtures, не в мире Foundry.

Обнаруженная при приватной проверке ошибка Foundry14 исправлена: новые сообщения используют core.messageMode/ChatMessage.applyMode, с fallback на старый API для прежних интеграций. Убрано принудительное превращение сообщений с сопротивлением в публичные; native HT сохраняет режим GGA. Старые публичные/приватные документы не переписываются.

## Подтверждённые проблемы до изменения

1. executeShot глубоко копировал Actor flags до проверки дубликата, ещё раз после броска, затем saveState снова копировал и передавал всю историю. Даже повтор старого attackId оплачивал копирование полного журнала. Большой ammoKey рецепта также остаётся законной частью квитанции и увеличивает стоимость этих повторов.
2. Обычная учитываемая атака after-attack сохраняла attackProfile и pendingShotSnapshot, затем ещё shotSnapshot. Итоговая запись не удаляла две прежние копии. Профиль повторялся примерно три раза, включая полные рецепты и вычисленные правила. В самом снимке верхние поля mode/ammunition тоже повторяют часть profile; они сохранены для совместимости.
3. Каждый новый attackId выполнял game.messages.contents.find по всем сообщениям, включая завершённые старые pending-снимки. contents дополнительно создаёт массив. После F5 это повторялось для каждой новой атаки.
4. Рендер одного и того же сообщения повторно строил чистое описание боеприпаса. Динамические права, combat-контекст, кнопки и действия при этом требуют свежей проверки; кешировать целиком HTML или право доступа было бы ошибкой.
5. В текущей Foundry14 core.rollMode — deprecated клиентская настройка. Живой тест показал, что её запись не задаёт режим штатного переключателя core.messageMode. Старый код мог создавать публичную атаку при выбранном другом штатном режиме; отдельное принудительное whisper=[]/blind=false у сопротивлений также нарушало требование приватности.

## Архитектура после изменения

**Actor.** copyAmmoResources копирует только рабочие поля, исключая журнал. writeAmmoResources для настоящего Actor Document передаёт отдельные поля ресурса и только одну квитанцию через один Actor.update. Изменение магазина не передаёт ни одной старой квитанции. Отсутствующие в устаревшей форме неизвестные поля не удаляются. Чтение журнала остаётся прямым по attackId, до копирования ресурсов; публичный loadState по умолчанию по-прежнему умеет вернуть полную историю, includeHistory=false — только ресурсы.

Перед нативным выполнением подтверждённого запроса сохраняется маленькая квитанция status=pending без расхода. При успехе единый Actor.update атомарно записывает новые ресурсы и полную квитанцию status=committed. При явном rolled=false снимается только эта неиспользованная отметка. При неоднозначном обрыве pending не удаляется автоматически: после F5 повтор отклоняется IncompleteShotAccounting, даже если сообщение ещё не существовало или было удалено. Старые квитанции без status считаются завершёнными, как раньше. Старые literal ID с точками используют прежний совместимый fallback, а не интерпретируются как путь update. Новые UUID допускают точечную запись.

**ChatMessage.** Для новой записи shotStorageVersion=2 начальный профиль находится только внутри pendingShotSnapshot или shotSnapshot. После подтверждённого расхода один update сохраняет полный прежний version1 shotSnapshot и удаляет pendingShotSnapshot/attackProfile. Старые сообщения без маркера не сокращаются даже при штатном завершении старого pending. Suppression сохраняет необходимый prepaid profile в receipt; spraying завершает снимок и burstReceipt вместе. Ни формулы, ни результаты, ни provenance не пересчитываются.

**Поиск.** Первый запрос строит индекс actorId→attackId→messageId из существующих документов; create/update/deleteChatMessage обновляют его. Повторный поиск не перебирает чат. При замене коллекции старые хуки снимаются. Простые адаптеры без полного lifecycle API продолжают свежий линейный поиск, чтобы не кешировать неподтверждённое состояние.

**История.** WeakMap-кеш хранит только чистое описание сохранённого снимка, с ключом снимка/языка; update/deleteChatMessage его инвалидируют. Доступность самого сообщения и его источника проверяется до кеша при каждом обращении. Кнопки, текущий combat и разрешения не кешируются. Damage по-прежнему использует точный исходный профиль, а приватный источник — только reference без копии в публичный Damage.

**Граница гарантий.** Очередь Actor сериализует операции одного клиента и разделяется сервисами этого Actor. Pending закрывает обрывы и повтор после сохранённого намерения. Это **не распределённый compare-and-set**: два независимых клиента, одновременно начавшие один новый ID до получения чужой записи, остаются ограничением прежней клиентской архитектуры. Нового утверждения о межклиентной атомарной блокировке нет; долговечные квитанции из-за этого тем более не очищаются.

Это точный снимок уже dirty рабочего дерева, а не ошибочное сравнение с Git HEAD. После изменения тот же runner работает без loader. Большие одинаковые неизменяемые значения профиля разделяют fixture-память; JSON-размер каждого документа вычисляется полностью, с повторением всех сохранённых полей. Это не замер фактического heap Foundry.

Команды воспроизведения на этой машине: задать OLEGURPS_HISTORY_BASELINE=%TEMP%/olegurps-shot-history-baseline и выполнить node --import ./tools/shot-history-benchmark-loader.mjs tools/benchmark-shot-history.mjs; затем снять переменную и выполнить node tools/benchmark-shot-history.mjs. Baseline/сырые JSON/TAP временные; для чтения отчёта дополнительные файлы не нужны.

## Ограничения и дальнейшие шаги

Сама долговечная Actor-история остаётся линейной по числу запросов. Удаление/TTL не доказаны безопасными и не применяются. Устраняется её повторное клиентское копирование и пересылка, но не гарантируется сокращение внутренней записи серверной БД: для этого требуется отдельное измерение storage backend. Первичная загрузка Actor и старых тяжёлых ChatMessage, а также явное полное loadState, всё ещё читают исторические данные.

Чистый кеш не является авторитетным источником истории и исчезает при F5. Холодная индексация старого чата O(N). Глобальной межклиентной CAS/блокировки на сервере нет; гарантия очереди ограничена одним клиентом, долговечные ID защищают завершённые/отмеченные операции после обновления данных. Неоднозначные pending нельзя автоматически освобождать: их расход требует выяснения, новый Roll тем же ID запрещён. Новые UUID поддерживают durable intent; необычные literal legacy ID оставлены на прежнем fallback.

Реальная Foundry проверена на небольшом числе временных объектов. Стресс10000 не запускался в мире; синтетические p50/p95 не называются latency живого сервера. Следующий отдельный этап при необходимости уменьшить сам Actor — авторитетное долговечное хранилище ID с атомарной межклиентной регистрацией и прежними OWNER-правами, с собственными crash/recovery проверками. Переносить старую историю или удалять receipts без такого доказательства нельзя.

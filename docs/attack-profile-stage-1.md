## API и состав данных

```js
const resolver = new AttackProfileResolver({ catalogs, compatibility });
const profile = resolver.resolve({
  actorId, weaponId, attack, rawAttack, state,
  binding, ammunition, context
});
const snapshot = createShotSnapshot(profile, {
  attackId, spent, resourceTiming, resourceReceiptId, messageId
});
```

`attack` — эффективный режим, уже обработанный существующим модулем. `rawAttack` — отдельная текущая запись `Actor.system.ranged`, до overrides. `state` — сохранённые настройки AmmoService. `binding` — результат проверки WeaponCatalogBindingService, а не автоматическое предложение модели. `ammunition` — результат `AmmoService.readAttackAmmunition(weaponId)`.

Resolver возвращает глубокую замороженную копию, не изменяя Actor, исходный режим, каталоги или AmmoService:

| Поле | Содержание |
| --- | --- |
| `version`, `actorId`, `weaponId`, `mode` | Версия профиля, Actor, оружие, UUID/path/name/mode GGA |
| `raw` | Исходные данные текущего режима GGA |
| `overrides` | Действующий override конкретного режима |
| `effective` | Данные текущей атаки после существующей обработки модуля; Damage и Range остаются исходными GGA |
| `ammunition` | status, source, book, kind, ammoId, ammoKey, name, подтверждённый familyId; recipe сейчас null |
| `resource` | Физический магазин либо legacy/unmanaged, стабильный magazineId, legacyIndex, доступные патроны, общий запас, ammoKey |
| `binding`, `compatibility` | Подтверждённая модель/режим, статус совместимости, причины и явная каталожная связь |
| `sources` | Источники данных; `catalogStatisticsApplied: false` |
| `transformations` | Только уже существующие overrides, с уникальными ID; никаких новых патронных преобразований |
| `context` | Режим выполнения, Token/сессия, физические выстрелы и существующие параметры броска |

Ammo-item и ammo-family различаются полем `kind` и отдельными ключами. Семейство читается из достоверной записи каталога. Рецепты, которые текущая модель не определяет, не придумываются. Legacy ammoType сохраняется как legacy, неизвестные/тестовые данные — unresolved; отсутствие каталога — unavailable. Совместимость undetermined не становится compatible. Достоверный incompatible останавливает бросок и расход.

Снимок содержит `attackId`, весь профиль, Actor/режим, magazineId, идентичность патрона, фактический `spent`, момент расхода, ID квитанции и `correlation`. Для обычного выстрела `correlation.attackMessageId` — ID созданного штатного сообщения. `damageMessageId: null` и `nativeDamageLink: "unlinked"` явно обозначают ограничение этапа.

Объекты resolver/snapshot заморожены внутри модуля. На границе записи Document flags передаются отдельные копии: Foundry 14 очищает входные объекты на месте. Это не изменяет исходный профиль.

`pendingShotSnapshot` хранит предварительную запись. Если присутствует `shotSnapshot`, именно он является завершённым снимком с фактическим расходом; предварительная запись не используется как доказательство списания.

## Выбор магазина и защита расхода

Источник — `flags.world.gurpsAmmoManager`, затем `ammunitionInventory.installedId` → конкретный magazine → `ammoKey` → stock.type. Текст окна и строка калибра не используются для идентификации. Чтение не выполняет миграцию или исправление старых данных.

`AmmoService.executeShot({ weaponId, attackId, prepare, execute, ... })` использует ту же очередь Actor, что install/load/unload. Внутри очереди читается актуальное состояние, строится профиль, проверяется совместимость и количество, выполняется существующий бросок, повторно проверяется ресурс и сохраняется расход только исходного магазина. После отмены подготовки или отказа GGA `canRoll` расход отсутствует. Физические патроны и число отдельных снарядов RoF не смешиваются.

Одновременные вызовы с одним attackId объединяются. После успешного сохранения повторный ID обнаруживается в `shotReceipts`, включая повторное открытие окна/сервиса. Успешные Promise не накапливаются в памяти. Квитанция расхода и ресурс записываются одним обновлением состояния AmmoService; устаревший Save настроек сохраняет актуальные квитанции и физический инвентарь.

Если сообщение уже создано, а сохранение расхода завершилось ошибкой, оно остаётся с `pendingShotSnapshot`, без ложного завершённого снимка. Повтор того же ID после перезагрузки блокируется по этому сообщению. Автоматическое повторение броска или списания при такой ошибке отсутствует.

Очередь действует в клиентском экземпляре Foundry. Изменение ресурса извне во время броска обнаруживается повторным чтением; такое событие останавливает автоматическое списание и требует проверки уже выполненной атаки. Распределённая транзакция между одновременно действующими клиентами не реализована и не проверялась этим этапом.

Существующие особые правила сохранены:

- Spraying: при бросках по целям патроны не списываются. Первый выполненный бросок закрепляет магазин/патрон; подмена магазина до следующих бросков или завершения блокируется. Списание всей очереди остаётся в `finish()`, один раз. После него отдельные снимки получают выделенный цели расход, а `burstReceipt` хранит общий расход и traverse waste. При отмене расход остаётся нулевым по прежним правилам. Повтор завершения после ошибки удаления сессии не списывает повторно, в том числе для legacy.
- Suppression: вся очередь оплачивается при активации. Профиль и квитанция сохраняются в существующей сессии и зеркалируются в Region. Последующие атаки используют этот профиль независимо от сегодняшнего магазина; их дополнительный расход равен нулю. Старая оплаченная сессия без этих метаданных остаётся неопределённой, без приписывания нового патрона.
- Атаки без управляемого физического магазина используют поддерживаемый путь FireService/GGA с `unmanaged`, без создания патронов или новой модели расхода для энергоружия/ракет.

## Фактическая интеграция GGA и ARCH

Подготовленный бросок по-прежнему использует существующий `executePreparedGgaRoll`, шаблон `systems/gurps/templates/die-roll-chat-message.hbs`, нативные Roll/ChatMessage и обработку прав/rollMode. В сообщение добавляются только собственные flags: `attackProfile`, `pendingShotSnapshot`, затем завершённый `shotSnapshot`. Новая независимая карточка не создаётся. Публичность, GM/blind/whisper сохраняются.

Изучены установленные `gurps-wiring.js`, `gurps.js`, `dierolls/dieroll.js`, `damage/resolve-damage-roll-action.js`, `damage/roll-damage.js`, `damage/damagechat.js` и штатный шаблон сообщения.

| Риск | Результат проверки этапа |
| --- | --- |
| ARCH-02 | Подтверждён путь `D:"name(mode)"`, повторно читающий атаку Actor. DamageChat не получает originating attack ID; диалог количества урона использует `GURPS.lastTargetedRoll`. Снимок конкретного попадания реализован, полная корреляция урона не заявляется |
| ARCH-03 | Физические магазины и отдельные stocks уже были реализованы в актуальном AmmoService v10. Числовые magazines — проекция для существующего интерфейса. Новая миграция не добавлена; legacy сохраняется |
| ARCH-05 | Дополнительные AP/APDS/HP/HEAT/HT64-преобразования не применяются. Имеющиеся Damage/armor divisor из GGA не преобразуются повторно |
| ARCH-06 | Собственные метаданные сохраняются внутри штатного сообщения. Новые эффекты, карточки, автоматические HT/Will/Affliction, Linked/Follow-Up отсутствуют |

Следующая необходимая точка интеграции: захват originating ChatMessage ID/attackId у конкретного клика штатной ссылки Damage **до await**, передача этого ID через GGA action/options до DamageChat.create и создаваемого им ChatMessage. Нужно проверить Actor/режим и видимость источника, затем читать профиль по явному ID. Глобальный «последний патрон», сопоставление по времени или последнему сообщению Actor для этого не подходят. На этом этапе GGA не перехватывается и формулы урона не подменяются.
